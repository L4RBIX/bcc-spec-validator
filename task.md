# Замечания перед Этапом 1 и ответ на вопрос про словари

## Ответ про словари (тиын, карты, счета)

Да, так можно, твоё предложение принято. Запрет в CONTEXT.md касается подгонки ЛОГИКИ под выданный документ,
а не общих справочников. Условия:

- валюты широко: KZT, RUB, USD, EUR, UZS, KGS, каждая со своей дробной единицей (тиын, копейка, цент и т.д.);
- идентификаторы широко: card, pan, account, iban, contract, client и русские формы (карт, счёт, договор, клиент);
- в начале каждого файла rules_data/* комментарий: "Универсальный справочник, не привязан к конкретному ТЗ";
- grep-проверку на слова из ТЗ делай по validator/*.py (логика), rules_data/ из неё исключи и перечисли отдельно,
  какие слова из ТЗ попали в справочники и почему.

Severity по умолчанию из твоего плана принимаю.
Одна правка: плейсхолдер в техническом поле (URL, endpoint, Swagger, адрес среды) = major, в остальных minor.

## Четыре замечания

1. Эвристика "короткая жирная строка = заголовок" рискованна на чужих ТЗ ("**Важно:**", "**Примечание**").
   Ограничь: только если строка не заканчивается двоеточием и не длиннее 40 символов. Тест на оба случая.

2. Правило 7 не должно зависеть от kind=heading. Коды статусов ищи в любых блоках внутри раздела, похожего на API
   (есть HTTP-метод, URL или слово "статус"/"status"). Иначе на другом ТЗ правило молча промолчит.
   Тест: синтетическое API, где коды статусов написаны обычными абзацами.

3. Для теста на ложные срабатывания создай сам синтетическое "чистое" ТЗ tests/fixtures/clean.md:
   другой домен (например, лимит переводов между своими счетами), все поля заполнены, есть версия и дата,
   нет размытых слов, единицы одни, корректный POST API со списком статусов, совпадающим с примерами.
   Все правила на нём должны дать 0 находок.

4. У находок правил поля problem, question, options, fix должны быть осмысленными, а не "обнаружен плейсхолдер".
   Шаблон на каждое правило с подстановкой цитаты и раздела. Пример:
   problem: "В разделе «X» поле «Y» не заполнено (стоит прочерк)."
   question: "Какое значение поля «Y» должно быть в разделе «X»?"
   options: ["Указать значение", "Пометить как «не применимо» с причиной"]
   fix: "Заполнить поле «Y» или явно указать, почему оно не применимо."
   impact: что не сможет сделать разработчик или тестировщик без этого.
